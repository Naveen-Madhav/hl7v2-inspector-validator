# Evaluation: what the validator can establish

The evaluation asks whether the implemented checks locate known defects without rejecting selected legitimate variations. It uses synthetic messages only. No patient records, employer interface logs, or operational outcomes were collected. The scope is three HL7 v2.5.1 scenarios: ADT-A01 admission, ORM-O01 patient laboratory order, and ORU-R01 patient laboratory result. Required laboratory segments are project profile decisions, not claims about every message allowed by the standard.

The benchmark contains 24 independently specified expected outcomes in `tests/cases.py`: three clean baselines, 15 defect cases, and six positive edge cases. Each defect targets one rule family. The positive cases cover reduced date precision, fractional seconds with a timezone, a Unicode single-component name, repeated laboratory order groups, custom delimiters, and an explicit-null optional field. Expected rule sets are written into the cases rather than generated by the validator. Defect cases also specify the principal location and severity. Clean cases must finish with complete coverage and no issues, preventing an unparsed message from being counted as a successful clean result.

Running `scripts/evaluate.py` produced 24 matching outcomes out of 24 cases. The machine-readable record is `docs/benchmark_results.json`. That result measures agreement with this authored benchmark, not accuracy across real hospital traffic. The six sample-library fixtures also have independently declared expected rule sets, and automated tests check each one. Separate tests exercise unsupported versions and message types, repeated result groups, input boundaries, malformed headers, unclosed escapes, and export safety. Unsupported inputs remain inspectable where possible, with an explicit notice that validation coverage is limited.

The checks distinguish several failure mechanisms that are easy to blur during interface debugging. A missing PID-3 identifier is different from identifier metadata without an identifier value. A timestamp can have the right digit count and still contain an impossible calendar date. An OBX value can be readable text yet contradict the NM datatype declared in OBX-2. Reversed ORC/OBR segments can undermine a laboratory order's grouping even when all required segment names appear somewhere in the message. These examples explain why parsing success alone is insufficient: a parser can construct an object without establishing that the message fits the intended receiving workflow.

Correctness also depends on avoiding overstrict assumptions. A single-component name and Unicode text should not fail merely because an example used a Western family/given-name pair. Reduced date precision can be legitimate. Repeated order groups must restart at a valid group boundary rather than be treated as duplicate singleton segments. Implementation testing exposed an ordering defect that treated the first OBR as a repeated-group start; the grammar now requires a later occurrence and a completed preceding group. The regression cases cover both repeated valid groups and invalid ordering. This is a concrete correction observed during development, not a claimed operational benefit.

Several limitations remain. The benchmark is small and authored alongside the implementation, so independent review and unseen test messages would provide stronger evidence. The validator does not check the entire HL7 grammar, every required field, vocabulary membership, transport acknowledgements, patient identity, or clinical plausibility. Coded values receive structural checks, not confirmation that a code exists in a terminology. Other OBX datatypes and extra segments trigger coverage notices. A clean report therefore means only that the selected implemented checks found no issues.

For educational use, the artifact offers inspectable examples and explanations that an instructor could use in an interoperability debugging exercise. This evaluation establishes software behavior on specified synthetic cases. It does not establish learning gains, usability with students, or readiness for clinical deployment. For a career interview, the same evidence supports discussion of profile design, diagnostic reasoning, negative testing, and the boundary between a useful validator and a complete conformance system.
